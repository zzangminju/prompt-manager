## 7. Git 커밋 및 브랜치 기록

### 커밋을 기능 단위로 나눈 기준

"한 커밋은 하나의 완결된 기능 변경"을 원칙으로 삼았습니다. 기능 하나를 구현하고
동작을 확인한 뒤 커밋했기 때문에, 커밋 메시지만 봐도 어떤 기능이 언제 추가됐는지
추적할 수 있습니다. 이렇게 하면 문제가 생겼을 때 어느 커밋에서 문제가 시작됐는지
찾기 쉽고, 특정 기능만 되돌리기도 편합니다.

`git log --oneline --graph` 결과는 다음과 같습니다.

```
* 잘못된 입력 안내 메시지 개선
* README 작성: 프로그램 설명, 실행 방법, 기능 목록 추가
* 즐겨찾기 추가/해제 및 즐겨찾기 목록 기능 작성
* 상세 보기 기능 작성
* 검색 기능 작성
* 카테고리별 조회 기능 작성
* 프롬프트 추가 기능 작성
* 기본 프롬프트 데이터 3개 추가 및 목록 보기 기능 작성
* 메뉴 화면과 프로그램 기본 구조 작성
* 프로젝트 초기 설정 및 README 작성
```

### 브랜치 생성 및 병합

프롬프트 추가 기능은 `feature/add-prompt`라는 별도 브랜치에서 작업한 뒤 `main`에
병합했습니다.

```
> git checkout -b feature/add-prompt   # 새 브랜치 생성 및 이동
   ... (기능 구현 및 커밋) ...
> git checkout main                     # main으로 복귀
> git merge feature/add-prompt          # main에 병합
```

### 브랜치 분리 이유 및 병합 시점/기준

새 기능을 만들다 보면 코드가 불안정해지는데, 이를 곧바로 `main`에서 작업하면 언제든
동작해야 할 기본 코드가 망가질 위험이 있습니다. 그래서 새 기능은 별도 브랜치에서
작업해 `main`을 항상 안정적으로 유지했습니다. 병합 시점은 "해당 기능이 완성되고
실행 테스트까지 통과한 직후"로 잡았습니다. 미완성 코드를 `main`에 섞지 않기 위한
기준입니다.

## 8. 코드 구조 (함수 분리 기준과 역할)

모든 코드를 한 함수에 몰아넣지 않고, 기능 단위로 함수를 분리했습니다. 각 함수는
"하나의 기능만 담당한다"는 기준으로 나누었습니다.

| 함수 | 역할 |
| --- | --- |
| `show_menu()` | 메뉴 화면 출력 |
| `show_list()` | 전체 프롬프트 목록 출력 |
| `add_prompt()` | 새 프롬프트 입력받아 추가 |
| `show_by_category()` | 카테고리별 조회 |
| `search_prompt()` | 키워드 검색 |
| `show_detail()` | 번호로 상세 내용 출력 |
| `toggle_favorite()` | 즐겨찾기 켜기/끄기 |
| `show_favorites()` | 즐겨찾기 목록 출력 |
| `main()` | 메뉴 반복 및 각 기능 연결 |

함수를 나눈 이유는, 기능별로 코드가 분리되어 있으면 특정 기능을 수정할 때 그 함수만
보면 되고, 다른 기능에 영향을 주지 않기 때문입니다. 또한 `main()`이 각 함수를
호출하는 구조라 프로그램 전체 흐름을 한눈에 파악할 수 있습니다.

## 9. 프롬프트 데이터 구조 (필드 구성·접근 방식·자료구조 선택 이유)

### 필드 구성과 접근 방식

프롬프트 하나는 딕셔너리로 표현하며, 다음 네 개의 필드를 가집니다.

```python
{
    "title": "블로그 글 작성",      # 제목
    "content": "...",              # 내용
    "category": "텍스트 생성",      # 카테고리
    "favorite": False              # 즐겨찾기 여부 (True/False)
}
```

각 필드에는 이름표(key)로 접근합니다. 예: `p["title"]`은 제목, `p["favorite"]`는
즐겨찾기 여부를 반환합니다.

전체 프롬프트는 이 딕셔너리들을 리스트에 담아 관리합니다.

```python
prompts = [ {...}, {...}, {...} ]
```

### 리스트와 딕셔너리를 선택한 이유

- **딕셔너리**: 프롬프트 하나에는 제목·내용·카테고리·즐겨찾기처럼 서로 다른 성격의
  정보가 들어갑니다. 이름표(key)로 접근하면 `p["title"]`처럼 의미가 분명해 코드가
  읽기 쉽습니다. 순서에 의존하는 방식보다 실수가 적습니다.
- **리스트**: 프롬프트는 여러 개이고, 목록을 순서대로 보여주거나 번호로 선택하는
  기능이 필요합니다. 리스트는 순서가 있고 번호(인덱스)로 접근할 수 있어 이 용도에
  적합합니다. 또한 `append()`로 새 프롬프트를 쉽게 추가할 수 있습니다.

즉 "여러 개(리스트) × 각각 여러 속성(딕셔너리)"이라는 데이터 성격에 두 자료구조의
조합이 가장 자연스럽습니다.

## 10. 입력 검증 로직 (위치·동작)

사용자 입력이 잘못됐을 때를 대비해 여러 곳에서 검증을 합니다.

- **빈 값 검증 (`add_prompt`)**: 제목·내용이 비어 있으면 `while` 반복으로 다시
  입력을 요청합니다.
  ```python
  title = input("제목: ").strip()
  while title == "":
      print("제목은 비워둘 수 없어요.")
      title = input("제목: ").strip()
  ```
- **번호 유효성 검증 (`show_detail`, `toggle_favorite`, 카테고리 선택 등)**:
  입력이 숫자인지, 그리고 실제 존재하는 범위 안인지 함께 확인합니다.
  ```python
  if not (choice.isdigit() and 1 <= int(choice) <= len(prompts)):
      print("잘못된 번호예요.")
      return
  ```
- **메뉴 선택 검증 (`main`)**: 정의되지 않은 번호를 입력하면 안내 메시지를 출력하고
  다시 메뉴를 보여줍니다.
  ```python
  else:
      print("잘못된 번호예요. 0부터 7 사이의 번호를 입력해주세요.")
  ```

검증을 각 기능 함수 안에 두어, 잘못된 입력이 들어와도 프로그램이 멈추지 않고
안전하게 다시 안내하도록 설계했습니다.

## 11. 메뉴 반복(while) 사용 이유 및 종료 조건 설계

메뉴는 `main()` 안의 `while True`로 반복됩니다.

```python
def main():
    while True:
        show_menu()
        choice = input("번호를 선택하세요: ")
        if choice == "1":
            show_list()
        # ... 중략 ...
        elif choice == "0":
            print("프로그램을 종료합니다. 안녕히 가세요!")
            break
        else:
            print("잘못된 번호예요. 0부터 7 사이의 번호를 입력해주세요.")
```

콘솔 프로그램은 사용자가 한 기능을 쓰고 나면 다시 메뉴로 돌아와 다음 기능을 고를 수
있어야 합니다. `while True`는 이 "계속 반복"을 구현합니다. 종료 조건은 사용자가 `0`을
입력했을 때이며, 이때 `break`로 반복을 빠져나가 프로그램을 끝냅니다. 종료를 사용자
입력에 맡김으로써, 원할 때까지 여러 기능을 반복해서 사용할 수 있습니다.

## 12. 검색 기능 구현 방식

검색은 입력받은 키워드가 프롬프트의 **제목 또는 내용**에 포함되어 있는지를 확인하는
방식으로 구현했습니다.

```python
for p in prompts:
    if keyword in p["title"] or keyword in p["content"]:
        # 검색 결과에 포함
```

파이썬의 `in` 연산자는 어떤 문자열이 다른 문자열 안에 들어 있는지를 검사합니다.
제목과 내용 두 곳을 `or`로 함께 검사하므로, 제목에 없더라도 내용에 키워드가 있으면
검색됩니다. 결과가 하나도 없으면 "검색 결과가 없어요." 안내를 출력합니다.

## 13. 데이터 유지 설계 및 파일 형식 선택

현재 프로그램은 데이터를 **메모리(리스트)**에만 저장하며, 프로그램 실행 중에는
추가·즐겨찾기 상태가 유지되지만 종료하면 초기화됩니다. 이는 과제 요구사항("종료 시
초기화")에 맞춘 설계입니다.

만약 데이터를 영구적으로 유지해야 한다면, 프롬프트 데이터가 제목·내용·카테고리·즐겨찾기
같은 구조를 가진 딕셔너리 목록이므로 **JSON 파일** 형식이 가장 적합합니다. JSON은
파이썬의 리스트·딕셔너리 구조를 거의 그대로 저장하고 다시 불러올 수 있어, 별도의 복잡한
변환 없이 `json` 모듈로 저장(`json.dump`)·불러오기(`json.load`)를 할 수 있기
때문입니다. 프로그램 시작 시 파일을 읽어오고, 데이터가 바뀔 때마다 파일에 다시 저장하는
방식으로 확장할 수 있습니다.

---

## 14. 동일 제목 프롬프트 충돌 처리 규칙

현재 구현에서는 제목이 같은 프롬프트도 각각 별개로 리스트에 추가되며, 번호(순서)로
구분되므로 실행에는 문제가 없습니다. 다만 사용자가 헷갈릴 수 있으므로, 확장한다면
다음 규칙을 적용할 수 있습니다.

- 추가 시 기존 목록에 같은 제목이 있는지 검사하고, 있으면 "같은 제목이 이미 있습니다.
  그래도 추가할까요?"라고 사용자에게 확인을 받습니다.
- 또는 제목 뒤에 자동으로 번호를 붙여(`제목 (2)`) 구분되도록 합니다.

핵심 규칙은 "데이터를 덮어쓰지 않고, 사용자에게 선택권을 주거나 구분 가능한 형태로
저장한다"입니다.

## 15. 병합 충돌(merge conflict) 발생 시 해결 순서

두 브랜치가 같은 줄을 다르게 수정하면 병합 시 충돌이 발생합니다. 해결 순서는 다음과
같습니다.

1. `git status`로 충돌이 난 파일을 확인합니다.
2. 해당 파일을 열면 `<<<<<<<`, `=======`, `>>>>>>>` 표시로 양쪽 변경 내용이
   나뉘어 있습니다.
3. 두 내용을 비교해, 최종적으로 남길 코드를 직접 정하고 충돌 표시 기호를 모두
   지웁니다.
4. 정리한 파일을 `git add`로 담고 `git commit`으로 병합을 마무리합니다.

원칙은 "충돌 표시를 남겨두지 않고, 어떤 코드를 남길지 사람이 판단해 하나로 합친 뒤
커밋한다"입니다.

## 16. 카테고리 체계 변경 시 안전한 수정 방법

카테고리 목록은 코드 상단의 `categories` 리스트 한 곳에서 관리합니다.

```python
categories = ["텍스트 생성", "이미지 생성", "영상 생성", "페르소나", "자동화", "기타"]
```

카테고리를 추가·변경하려면 이 리스트만 수정하면 됩니다. 메뉴 출력과 카테고리 선택은
모두 이 리스트를 기준으로 자동 처리되므로, 여러 함수를 일일이 고칠 필요가 없습니다.
이렇게 "설정 값을 한 곳에 모아두는" 방식은 유지보수 시 수정 지점을 최소화하고 실수를
줄여 줍니다.

단, 이미 등록된 프롬프트가 옛 카테고리 이름을 가지고 있을 수 있으므로, 카테고리 이름을
바꿀 때는 기존 데이터의 `category` 값도 함께 갱신하는 것이 안전합니다.
